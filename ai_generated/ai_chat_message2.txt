Existing users: no, that was a genuine gap — the original code could only build state by calling observe() live, with no way to rehydrate a returning user from stored scores. That's now fixed with two constructors:

from_events(graph, events) — replays the answer log. This is the one to use if you persist every answer in Postgres as the source of truth (which is the design I sketched earlier); it reproduces the exact belief state and counts with no ambiguity.
from_state(graph, mastery, counts=…) — rehydrates from a persisted belief snapshot. Pass only the concepts that carry real evidence; everything else keeps its dynamic prerequisite-gated prior so it can still react to new answers.

On the "next series of concepts" phrasing: the live loop deliberately picks one concept at a time and re-selects after each answer, because each answer changes the belief and therefore the optimal next probe — a fixed pre-planned series would throw away that adaptivity. But for a roadmap or progress map I added preview_path, which returns the ordered series of distinct concepts it would walk from the current state (optimistically assuming mastery). From the zero state that gives you the foundations-first ordering (select → where → joins → subqueries → group_by → …); from a populated state it excludes what's already mastered and returns just the remaining path. That preview is also a clean fit for your earlier cold-start-fatigue concern: you can cap it and show the user a bounded plan instead of an open-ended quiz.
